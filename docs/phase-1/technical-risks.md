## 2. Technical risks

Severity: **H** (could block or endanger the pilot) · **M** (needs active
management) · **L** (watch).

| ID | Risk | Sev | Impact | Mitigation | Owner / trigger to revisit |
|----|------|-----|--------|-----------|----------------------------|
| TR-1 | **eTIMS integration uncertainty** — the API mode (OSCU/VSCU/eTIMS-Lite/middleware), required fields, and sandbox access are unknown (legal-scope §3.2 — REQUIRES VALIDATION). | H | Weekly commission invoices may not be truly eTIMS-compliant at go-live. | `EtimsService` adapter interface; a **`MANUAL_REFERENCE` fallback** — generate a compliant-format invoice, an admin keys it into the KRA portal and records the reference; no statement is blocked. Tax-advisor engagement is on the legal checklist. | Founder + tax advisor; before first real statement |
| TR-2 | **WhatsApp BSP onboarding lead time + template approval** — BSP account setup, business verification with Meta, and per-template approval can take weeks. | M | WhatsApp channel unavailable at go-live. | Start BSP onboarding in Phase 2 week 1. **SMS fallback is automatic** for every WhatsApp message; nothing depends on WhatsApp exclusively. In-app inbox always written. | Phase 2 lead |
| TR-3 | **Data residency** — no low-cost, acceptable-region **managed** PostgreSQL may exist for Kitengela/Kenya (legal-scope §3.4 — REQUIRES VALIDATION via DPIA). | H | Compliance exposure, or higher ops burden if self-managed. | Region chosen for residency first (deployment §7); **app-level envelope encryption** for HIGH-PII so region is not the only control; self-managed Postgres + disciplined backups as the fallback; DPIA to confirm the position. | Founder + data-protection advisor; before onboarding real users |
| TR-4 | **Low-end-device PWA reliability** — camera capture, IndexedDB quotas, service-worker behaviour on old Android WebView; **iOS PWA** lacks Web Push and limits background. | M | Drivers can't reliably complete custody steps; recipients can't use the link. | Device-lab test on representative Kitengela-tier phones in Phase 2 iteration 1; **SMS carries every critical OTP/link step** so nothing time-critical needs Web Push; the Svelte spike is the contingency if the React bundle is the problem; offline queue is deliberately tiny. | Phase 2 lead; device-lab results |
| TR-5 | **Single VPS = single point of failure** vs NFR-AVAIL-1 (~99%). | M | Full outage until restore (RTO ≤ 8 h target). | Managed Postgres with PITR; daily backups off-host; **rehearsed restore runbook**; fast redeploy (compose). Accepted for the pilot (security-architecture §7). | Any scaling decision |
| TR-6 | **SMS provider outage impacts OTP login** (OTP is SMS-primary). | M | Users (and admins' first factor) can't log in. | A **second SMS provider behind the same `SmsGateway` interface**, config-selectable, as a fast follow; WhatsApp OTP as an optional secondary if `config.otp.whatsapp_enabled`; alerting on SMS failure rate. | Phase 2 (design the interface for two providers from the start) |
| TR-7 | **Offline-queue conflict UX** — a queued custody note replayed after the job was cancelled/advanced by someone else. | L | Driver confusion; a lost note. | Whitelist is tiny (advisory steps + photos only); conflicts are **surfaced in a "Sync issues" tray**, never auto-merged (brief §23); the gating proofs (OTP) are online-only so nothing unsafe is ever deferred. | — |
| TR-8 | **Optimistic-lock + row-lock + Celery retry interplay** under concurrency. | M | Rare double side effects or spurious `409`s. | `Idempotency-Key` on every mutation + a dedupe table; `SELECT job FOR UPDATE` serialises; handlers idempotent by `(handler, event_id)`; the state-machine + negotiation-race test suites are CI-required. | Testing |
| TR-9 | **Geocoding/distance coverage on Kitengela outskirts** (Isinya, Kisaju, Kaputiei) may be poor / costly. | M | Bad distance metrics, matching errors, cost. | `GeoService` adapter; **cache aggressively**; **ops manual distance override**; distance is a *metric + ranking input*, not a hard gate; a self-hosted OSRM option if a commercial provider is weak/expensive. Zones are deferred anyway (D-PIL-5) so proximity ranking starts coarse. | Phase 2; provider evaluation |
| TR-10 | **Audit hash-chain operational burden** — chain verification cost, off-box export reliability. | L | Missed tamper detection if the verifier silently fails. | Batch verification; the verifier result is itself a metric with a `CRITICAL` alert on failure or a break; monthly partitions keep ranges small; write-once export is a simple object-lock `PUT`. | Observability |
| TR-11 | **Trust auto-proposal on a thin early dataset** could propose progressions that don't reflect reality. | M | An under-tested operator reaches Elevated. | Progression is **admin-confirmed** (not auto-applied) — the confirmation queue is the real gate; `criteria_snapshot` + evidence links are reviewed; repeat-pair monitoring surfaces collusion; thresholds are configurable to tighten in-pilot. | Weekly pilot governance |
| TR-12 | **Group model creep** — pressure to add internal settlement/scheduling during the pilot. | L | Scope + timeline blow-out; the out-of-scope list (D-OPR-GRP-1) ignored. | The schema deliberately omits payroll/roster tables (database-design §7); "minimal group" is an explicit constraint in [domain-architecture.md](domain-architecture.md) §3.4; changes go through the decision log. | Founder / weekly review |
| TR-13 | **PostGIS availability on the chosen host.** | L | Proximity ranking + zone containment need a fallback. | If PostGIS is unavailable: `lat`/`lng` numeric columns + bounding-box pre-filter + haversine in SQL — workable at pilot scale (database-design §6). | Deployment; host choice |
| TR-14 | **M-Pesa paybill classification** — confirming a merchant paybill used only for the platform's **own** commission stays outside CBK PSP licensing (legal-scope §3.6 — REQUIRES VALIDATION). | H | Regulatory exposure if the arrangement is deemed "payment-service business". | The platform **holds no fare** by design (no wallet/escrow tables); settlement is **manual recording** in the pilot; written legal opinion + bank/PSP confirmation is on the pre-pilot legal checklist. | Founder + advocate; before collecting any commission |
| TR-15 | **Retention periods, lawful basis, consent wording, cross-border transfer basis** are all REQUIRES VALIDATION (legal-scope §3.4, §7). | H | Non-compliant processing if the pilot starts before these are set. | Every period is **config**, not code; the consent step + privacy notice + recipient short terms are content, drafted with counsel; **ODPC registration + DPIA are on the pre-pilot legal checklist and gate go-live** (legal-scope §9). | Founder + data-protection advisor |
| TR-16 | **Django + Node question** — if the founder prefers Node, the admin-surface cost (weeks) lands in Phase 2. | L | Timeline. | The design docs are framework-agnostic at the seam level (modules, state-machine, outbox, authz engine, ledger); a Node port is possible with the admin-scaffold cost noted (technology-stack §2). | Founder, at Phase 1 review |
| TR-17 | **KMS for a bootstrapped deployment** may be a guarded secrets-store key rather than a full managed KMS/HSM. | M | Weaker key isolation for HIGH-PII envelope encryption. | Documented key-rotation runbook; separate keys per env; upgrade to a managed KMS when budget/compliance requires (security-architecture §7). | Scale / compliance trigger |

## 3. Assumptions this architecture makes (and that could be wrong)

| Assumption | If wrong |
|-----------|----------|
| Pilot volume stays at hundreds of operators/businesses, low-thousands of jobs/month (NFR-PERF-1) | The single-VPS + single-worker topology needs to scale (add worker processes / a second host — no code change; the outbox + `SKIP LOCKED` support it) |
| The founder's operator network will tolerate a per-driver verification step, incl. for group members | Onboarding is slower; phase the cohorts (pilot-strategy §3) |
| Pickup contacts can receive an SMS and read a code to the driver at handover | The Standard-band operator-attested fallback carries more traffic; Elevated+ needs the in-app business-confirmation path used more |
| SMS is a reliable OTP channel in Kitengela | Add the second SMS provider + WhatsApp OTP sooner (TR-6) |
| A merchant paybill for own-commission is outside PSP licensing (TR-14) | Commission collection design changes; possibly a licensed-PSP partnership (future-roadmap) |
